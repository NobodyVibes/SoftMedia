# Manual QA — Phases 0 to 3 (browser features only)

**Date:** 2026-05-30
**Scope:** Every browser-facing feature touched in the Phases 0-3 work. Each step is grounded in the actual UI code (file:line references in italics) so the wording matches what's on your screen.

Server-only changes (forwarded-headers middleware, scope-authorization fail-closed, SSRF guards on webhooks, scheduled-tasks registry plumbing) aren't in this plan — they're covered by the automated test suite (635 server + 152 client tests pass).

---

## 0. Setup (do once)

1. Build and run the server (`dotnet run --project src/SoftMedia.Server`) — note the URL it prints (default `http://localhost:5011`).
2. Run the client. Two options:
   - **Dev mode** (`npm run dev` in `src/SoftMedia.Client`) — fastest, but **PWA + service worker do not run in dev**. Use this for everything except the PWA section.
   - **Production preview** (`npm run build && npm run preview` in `src/SoftMedia.Client`) — required for the PWA section below.
3. **You need at least two accounts**: one admin (for backup / scheduled tasks / OMDb / streaming caps / Fix Match) and one regular user (to confirm admin-only UI is hidden and to test the API-token / 2FA / webhook flows).
4. **Use Chrome or Edge** for everything that involves Cast or PWA install prompts — Firefox and Safari intentionally hide both.
5. Have a media library with at least: one movie that direct-plays, one that transcodes (e.g. HEVC 10-bit in plain Chrome), and one show with multiple episodes.

If anything in §1 fails the rest of the plan probably won't work, so do that block first.

## 1. Phase 1 — Admin dashboard (`/settings/admin`)

> **All three features live on the same page.** Sign in as admin → sidebar → Settings → Admin Dashboard. Cards stack top-to-bottom in this order: Backups, Background Tasks, then the API Usage card *(only renders if OMDb has been queried at least once today — won't appear on a fresh install)*.

### 1.1 Database Backups (P1-WI-001)
*Card with blue Database icon at top of `/settings/admin`. Component: [`BackupCard.tsx`](src/SoftMedia.Client/src/components/admin/BackupCard.tsx).*

**Happy path:**
1. Click **Create Backup** — button shows a spinning RefreshCw, then a green toast "Backup created" appears top-right. A new row appears in the table with a monospace ID, timestamp, and human-readable size (e.g. "12.4 KB").
2. Click the PinOff icon in the row's actions → swaps to a filled **blue** Pin glyph; tooltip changes from "Pin (protect from rotation)" → "Unpin".
3. Click the blue Download icon → browser downloads `softmedia-backup-<id>.zip`.
4. Click **Restore from File** → pick the zip you just downloaded → toast: *"Restore staged. Restart the server to apply."* (visible ~8 seconds).
5. **Stop and restart the server**, log in again. State matches the snapshot.

**Things that should feel right vs. wrong:**
- **Right:** double-clicking Create only fires once (button disables `opacity-50` while busy). Pin survives a page reload.
- **Wrong:** Pin reverts to PinOff after a refresh (server didn't persist). Downloaded zip is 0 bytes. Restore "succeeds" but server restart shows no state change (toast lied).

**Known limitations (these are intentional, not bugs):**
- Restores apply **only on next server start** — the toast says so. You won't see DB changes until you restart yourself.
- The zip contains hashed credentials + JWT signing key in `appsettings.json`. Treat it like a password.
- **No confirmation dialog** before restore — picking a file commits immediately. Pin a known-good backup if you're worried about misclicks.
- No Delete button. Cleanup is the rotation service's job; Pin is the only manual knob.

**Touch-target note:** Pin/Download icons are ~28×28 px — below the 44×44 mobile recommendation. Fine on desktop, cramped on phones.

### 1.2 Background Tasks (P1-WI-005)
*Card with blue Clock icon, second on `/settings/admin`. Component: [`ScheduledTasksCard.tsx`](src/SoftMedia.Client/src/components/admin/ScheduledTasksCard.tsx).*

**Happy path:**
1. Scroll to the card. Table has five columns: Task, Last Run, Result, Next Run, Actions.
2. **Last Run** column shows relative time: `Ns ago` / `Nm ago` / `Nh ago`, or `—` for never-run.
3. **Result** column: never-run = grey "never run"; success = green CheckCircle + "Success"; failure = red XCircle + "Failed".
4. If a row has a red error line under its name, hover it → native browser tooltip reveals the full error string.
5. On any task with a "Run now" button (small Play icon, primary color), click it → green toast "Task triggered". Within ~15 seconds the Last Run column updates without any visible reload.
6. Wait 15s without interacting → Last Run / Result / Next Run silently refresh in place.

**Edge cases worth checking:**
- **Event-driven tasks** (file watcher, queue consumers): Next Run column shows literal text "event-driven" — they never have a future timestamp.
- **No Run now button**: that task has `supportsManualTrigger = false`. Correct.
- **Next Run in the past**: shows "imminent" (overdue task).
- Click Run now rapidly multiple times → button stays disabled while busy; only one request fires.

**Right vs. wrong:**
- **Right:** Success/Failed badges have *matching* color and icon. Polling updates time strings without flashing or row reorder.
- **Wrong:** Failed task with a green Success badge. Run now stays disabled forever after success. Tasks list is empty (the `/admin/tasks` endpoint is failing silently — check Network tab).

**Known limitations:**
- 15-second polling cadence — newly triggered tasks may take that long to reflect their final result.
- Idle background sweeps (e.g. trickplay) show Success even when no work was needed.
- No inline log viewer — only the single-line `lastError`. Full logs are in the server's log files.

### 1.3 OMDb API Usage card (P1-WI-004)

## 2. Phase 1 — Streaming caps + per-user bitrate (P1-WI-003)

> These settings auto-render from the registry — there's no dedicated UI to QA, just verify they appear on the right tabs with the right labels.

1. **`/settings/playback/transcoding`** → scroll to bottom. Find "Max Simultaneous Transcodes Per User" with description *"Maximum concurrent transcode sessions per user. 0 = unlimited."* Set to 2, click Save → green "Settings saved successfully" toast.
2. **`/settings/playback/streaming`** → scroll to bottom. Find "Max Streaming Bitrate Lan" with description *"Maximum bitrate (kbps) for local (LAN) streaming. 0 = unlimited."* Set to 8000, Save.
3. Hard-reload both pages — values persist.

**Functional check (requires two clients):**
- Per-user cap: from User B's account, start 3 concurrent transcodes when cap is 2. Third should fail or fall back to direct play.
- LAN cap: stream from a LAN-attached client; bitrate should be capped to 8000 kbps not the WAN value.

**Known limitations / things that may feel wrong but are intentional:**
- Both fields use the **generic renderer** — plain number input with no "Mbps" or "Unlimited" hint. The prettier UI on the older `MaxStreamingBitrate` / `MaxSimultaneousTranscodes` fields is a special-case branch in [`SettingsPage.tsx`](src/SoftMedia.Client/src/pages/SettingsPage.tsx) that doesn't match the new keys.
- Both sort to the bottom of their group (not in the explicit display-order arrays).
- Bitrate values are **kbps**, not Mbps — the description string is the only place that says so.
- `0 = unlimited` but neither field renders that hint.

## 4. Account features (My Account page)

> Username menu top-right → **My Account**. Cards top-to-bottom: Account Info → Change Password → **Two-Factor Authentication** → **API Tokens** → **Webhooks** → Delete Account.

### 4.1 API Tokens (P1-WI-002)
*Component: [`ApiTokensCard.tsx`](src/SoftMedia.Client/src/components/account/ApiTokensCard.tsx).*

**Happy path:**
1. Click blue **New Token** (top-right of card) → inset panel opens with Label input, Scopes checkboxes, Create/Cancel.
2. Label placeholder reads "e.g. Home Assistant". 100-char max.
3. **As a non-admin user** scopes show three checkboxes: Read library (pre-checked), Read state, Write state. **No Admin scope.**
4. Click **Create Token** → a blue callout appears: *"Copy your token now — it will not be shown again."* with the raw token in monospace on a black background.
5. Click clipboard icon → swaps to a green check for ~2s. Paste somewhere to verify.
6. Click X → callout vanishes, token gone from screen forever.
7. Row appears in the list below: e.g. *"Home Assistant"* / *"read:library · never used"*. Trash icon on the right.
8. **Use the token:** from a terminal, `curl -H "Authorization: Bearer <sm_...>" http://localhost:5011/api/v1/account` → 200. Hard-refresh My Account → row subtitle now reads *"last used <timestamp>"*.
9. Trash icon → row vanishes immediately. Card shows "No API tokens yet." if it was the only one.

**Edge cases:**
- Uncheck every scope → Create Token button disables.
- Cancel during creation — no token minted, no row added.
- **Admin user** sees a 4th checkbox "Admin (admins only)". Mints an admin-scoped token.
- Empty label — server may accept (no client validation).

**Right vs. wrong:**
- **Right:** token shown only in the one-time blue callout. Form auto-closes after Create. Admin scope hidden from non-admins.
- **Wrong:** token visible anywhere outside the callout. "last used" never updates after a real API call (server isn't writing back). Copy shows a check even when clipboard write rejected (silent failure — check console).

**Known limitations:**
- Clipboard fails silently on insecure HTTP origins or if the user revoked clipboard permission.
- Scope rows show friendly labels ("Read library") but the token list shows raw strings ("read:library"). Cosmetic inconsistency.

### 4.2 TOTP 2FA enrollment (P2-WI-005)
*Card with shield icon. Component: [`TotpCard.tsx`](src/SoftMedia.Client/src/components/account/TotpCard.tsx).*

**Happy path — enroll:**
1. Initial state: purple shield-off icon + copy *"Add a second factor with an authenticator app…"* + blue **Enable 2FA** button.
2. Click Enable 2FA → spinner briefly → card swaps to enrolling state: 180×180 QR code on white background, *"Can't scan? Enter this key manually:"* + grey monospace secret, code input, Confirm/Cancel.
3. Scan QR with Google Authenticator / Authy / 1Password — entry rotates 6-digit codes every ~30 s.
4. Type the current code, click **Confirm** → spinner → recovery state with green text *"2FA enabled. Save your recovery codes now — they're shown only once."* + 2-column grid of monospace codes.
5. **Click Copy codes** → green check for 2s, codes copied to clipboard. **Paste them somewhere you trust now — they cannot be recovered.**
6. Click Done → card shows steady enabled state: green shield-check icon + *"2FA is enabled. You'll be asked for a code when you sign in."* + red Disable 2FA button.

**Happy path — login challenge:**
1. Log out (or open incognito). Go to `/login`, enter username + password → click Sign In.
2. Form swaps (everything but the header replaced): label "Authentication code" + input with placeholder *"6-digit code or recovery code"* + helper text + Verify button + small grey "Back to login" link. Input is **auto-focused**.
3. Enter current TOTP code from your authenticator → Verify → redirected to `/`.
4. Try again with a recovery code (instead of TOTP) — also works. **Then try the same recovery code a second time → rejected (one-time use).**
5. "Back to login" link clears the code + challenge, returns you to username/password.

**Happy path — disable:**
1. Click red **Disable 2FA** → password field + code/recovery field appear.
2. Enter password + current TOTP (or a recovery code) → Confirm Disable → card returns to un-enrolled state.

**Edge cases:**
- Wrong code on Confirm → red "Invalid code. Check your authenticator app and try again." Stays on enrolling screen.
- Wrong password on Disable → red "Could not disable 2FA. Check your password and code."
- Manual key entry (copy the secret instead of scanning QR) — same code works.
- 5+ wrong code attempts → "Too many attempts. Please wait a minute and try again." (HTTP 429 from rate limiter).

**Right vs. wrong:**
- **Right:** shield color changes (purple-off → green-check). Recovery codes shown exactly once. Disable requires *both* password AND code.
- **Wrong:** QR shows as broken image / blurry (QRCodeSVG not mounted). Status stuck on "disabled" after successful confirm (refresh invalidation broken). Disable succeeds with only password OR only code (server regression).

**Known limitations:**
- Recovery codes shown once, stored only as hashes. Lose them and your only recovery is to disable+re-enroll using your authenticator.
- Code input uses `inputMode="numeric"` even though the help text mentions recovery codes — on a phone you'll get the numeric keypad and have to switch to alphabet for an alphanumeric recovery code.
- No "Remember this device" — every login asks for a code.
- 2FA login screen reuses the same "Welcome Back" header; no explicit "2FA Required" marker.

### 4.3 Webhooks (P2-WI-004)
*Card with webhook glyph. Component: [`WebhooksCard.tsx`](src/SoftMedia.Client/src/components/account/WebhooksCard.tsx).*

**Setup:** open [webhook.site](https://webhook.site) in a separate tab — gives you a free one-click URL that accepts POSTs and shows them live.

**Happy path:**
1. Click blue **New Webhook** → form opens: URL input, three event checkboxes (Library scan completed (pre-checked), Library scan failed, Test events), Create/Cancel.
2. Paste your webhook.site URL. **Also tick "Test events"** (see Known Limitations below).
3. Click Create → blue callout appears with the signing secret in monospace. *"Signing secret — copy it now, it won't be shown again. Verify the X-SoftMedia-Signature header with it."* Form collapses.
4. Click clipboard icon → green check, secret copied.
5. Click X → callout dismissed. Secret gone forever from the UI.
6. Webhook row appears: URL + event list. Two icons on the right: paper-plane (send test) and trash (delete).
7. Click paper-plane → green toast "Test event enqueued". **Switch to webhook.site tab** — within a few seconds a POST appears with JSON body and `X-SoftMedia-Signature` header.
8. **Trigger a real event:** run a library scan from `/settings/admin`. After it completes, webhook.site shows another POST with `event: "library.scan.completed"`.
9. Hard-refresh My Account — webhook row now shows ` · last: 200` subtitle.

**Edge cases:**
- Create disabled with empty URL or zero events.
- Invalid URL (e.g. `not-a-url`) → red "Failed to create webhook" toast.
- **Sending a test to a webhook NOT subscribed to `webhook.test`:** toast still says "Test event enqueued" but no POST actually arrives on webhook.site. **This is intentional** — server only sends to subscriptions that include the event in their list. Always tick "Test events" on subscriptions you want to test-fire.
- Endpoint returns 500 → row subtitle shows ` · last: 500`. No UI retry button (server handles retry).
- **Verify HMAC:** copy the request body from webhook.site, compute `HMAC-SHA256(secret, body)`, compare to `X-SoftMedia-Signature` header.

**Right vs. wrong:**
- **Right:** secret only ever shown in the one-time blue callout. `last: <status>` appears after deliveries. Trash removes immediately.
- **Wrong:** secret appears in the row listing or anywhere outside the callout. Create button enabled with empty URL.

**Known limitations:**
- **No reachability check at create time** — you can save a URL that 404s and only discover it via the "last: 404" status.
- Secret never re-displayable — lose it and you must delete + recreate (and update your receiver with the new secret).
- No per-webhook edit screen — change events by deleting and recreating.
- No delivery log — only the most recent status. Past failures aren't enumerated.

## 5. Video player

### 5.1 Trickplay scrubber previews (P2-WI-001)
*Hooks: [`useTrickplay.ts`](src/SoftMedia.Client/src/hooks/useTrickplay.ts). Renderer: [`ProgressBar.tsx:170-201`](src/SoftMedia.Client/src/components/player/ProgressBar.tsx#L170).*

1. **Pick a movie that's been in the library more than ~10 minutes** (so the background sweep has baked its sprite sheet) and start playback.
2. Hover the progress bar without clicking → bar thickens slightly, timestamp tooltip appears in blue above the cursor. **No thumbnail yet — thumbnails only show while dragging.**
3. Press and hold left mouse, drag horizontally → a small bordered thumbnail (320×180-ish) appears above the timestamp, updating live as you drag. **Open DevTools → Network**: you should see ONE sheet image fetched (`trickplay/{id}/sheet-N.jpg`) and reused across drag positions — no per-frame requests.
4. Release mouse → thumbnail and tooltip vanish, video seeks, playback resumes if it was playing.
5. **Now repeat on a brand-new item** (no manifest yet) → after ~100ms hold, you see a slightly larger (160 px wide) live-extracted JPEG fetched from `/api/transcode/{id}/frame?time=...`. Briefly between rapid scrubs you'll see a small "Loading..." card.

**Edge cases:**
- Seek past the last sheet → silently falls back to on-demand frame, no broken image.
- **Touch / mobile drag**: thumbnail does **NOT** show. ProgressBar uses mouse events only. Seeking still works.
- **Keyboard seek** (Tab to bar, arrow keys, PageUp/Down, Home/End) → seeks but no preview tooltip. Intentional — no cursor to anchor the tooltip to.

**Right vs. wrong:**
- **Right:** sprite thumbnail appears instantly with no network delay (cached after first request). Recognisable scene change inside one sheet as you drag.
- **Wrong:** thumbnail stretched/squashed/cropped wrong (sheet geometry mismatch — server bug). Network tab shows a fresh `/frame` request per pixel of drag on an item that DOES have a manifest (auth/token mismatch in `useTrickplay`). Wrong scene for hovered time (off-by-one in interval math). Tooltip lingers after mouseup.

**Known limitations:**
- Sweep runs every ~10 minutes. Brand-new items use the on-demand fallback until the next sweep.
- Thumbnails only on drag, not hover.
- No touch support for the preview.
- Fallback frame requests are debounced 100 ms — fast scrubbing on a no-manifest item briefly shows "Loading..." between frames.

### 5.2 "Why is this playing this way?" explainer (P2-WI-002)
*Trigger button at [`VideoPlayer.tsx:1911-1925`](src/SoftMedia.Client/src/components/player/VideoPlayer.tsx#L1911). Modal: [`TranscodeExplanationModal.tsx`](src/SoftMedia.Client/src/components/player/TranscodeExplanationModal.tsx).*

2. Hover → tooltip "Why is this playing this way?". Icon brightens from white/70 to white.
3. Click → centered modal with dark/blurred backdrop, dark grey panel, blue info icon + bold title. X button top-right.
4. **For a Direct-Play item** (e.g. an MP4 H.264 file in Chrome): method line reads "Playing directly — no conversion needed." Single body paragraph explains your client supports the stream natively.
5. **For a Transcoded item** (e.g. HEVC 10-bit in plain Chrome): method line "Converting the stream for your device." ### 5.3 Chromecast sender (P3-WI-001)
*Hook: [`useCast.ts`](src/SoftMedia.Client/src/hooks/useCast.ts). Button at [`VideoPlayer.tsx:1871-1909`](src/SoftMedia.Client/src/components/player/VideoPlayer.tsx#L1871). SDK loaded by [`index.html:30`](src/SoftMedia.Client/index.html#L30).*

**Prerequisites:** Chrome or Edge (Firefox/Safari won't show the button). HTTPS in production (localhost exempt). A Chromecast / Google TV / Nest Hub powered on, on the same LAN. Allow popups/mDNS in Chrome.

**Happy path:**
1. Start playback in Chrome on a machine that can see the Chromecast.
2. **Cast button (TV with radio waves) appears between Speed and the explainer info button**, in grey (text-white/70). Tooltip on hover: "Cast".
3. Click → Chrome's native receiver chooser opens (system-styled popup listing nearby devices).
4. Pick a receiver → 2-4 seconds later receiver wakes, shows connecting splash, starts playback. Receiver background shows the item poster; metadata shows title + year as subtitle.
5. **Cast button turns blue (text-blue-400)**. Tooltip changes to "Casting to *Living Room TV*" (your receiver's friendly name). `aria-pressed` is now `true`.
6. Click the blue button → session ends, receiver returns to its idle splash, button back to grey.
7. **Reload mid-cast** (start cast, then F5) → after reload, button comes back already blue with the right receiver name (autoJoin works).

**Edge cases:**
- **Firefox / Safari**: button absent. No errors. Intentional.
- SDK blocked (ad-blocker, CSP, gstatic.com unreachable) → button absent. Console may show one `[Cast] init failed` warn.
- User cancels chooser (Esc) → console logs `[Cast] requestSession aborted`, no toast, button stays grey.
- No receivers on LAN → Chrome shows "No devices found".
- **127.0.0.1 trap**: if your dev server binds only to localhost, the receiver (on the LAN) can't reach the stream URL → receiver shows error. The player turns relative URLs into `window.location.origin`-absolute, so use the LAN IP, not 127.0.0.1.
- Plain HTTP in production → Cast SDK refuses to initialise.

**Known limitations:**
- **Chromium-only.** No Firefox/Safari/AirPlay/DLNA fallback.
- **HTTPS required in production** (localhost OK in dev).
- Uses Google's Default Media Receiver — receiver UI is generic, not SoftMedia-branded. No custom subtitle styling or chapter art on the TV.
- **Subtitle tracks selected in the browser do NOT carry over** to the cast session. Only video, default audio, title, subtitle text, and poster forward.
- **Playback position is not synced** — casting starts from the beginning of the stream URL, not your current position.
- SDK loaded WITHOUT Subresource Integrity — intentional, because Google ships that URL as a mutable always-latest build. Defense-in-depth lives at the CSP layer. Comment in [`index.html:22-28`](src/SoftMedia.Client/index.html#L22) spells this out.

### 6.2 Offline detector + OfflinePage

1. With the app open on any page, DevTools → **Network → Throttling → Offline**.
2. Within ~1 second the entire viewport replaces with the **OfflinePage**: dark gradient background, 80×80 rounded tile with the blue→purple brand gradient containing a white WifiOff icon, heading "You're offline", body explaining you need network, single **Retry** button with refresh icon.
3. Click Retry → page reloads. If still offline → OfflinePage renders again. If online → normal app.
4. **Switch throttling back to "No throttling"** → OfflinePage disappears automatically. No reload needed.
5. Hover Retry → slight opacity drop, hand cursor. Tab to it → blue focus ring.

**Edge cases:**
- **Cold start offline**: close tab → OS airplane mode (or DevTools offline) → open the installed PWA → SW serves cached shell, React boots, OfflinePage is the very first thing painted (no white flash of the normal app first).
- **Flap network**: toggle offline ↔ online rapidly → OfflinePage appears/disappears in lockstep, no stuck state, no listener leak.
- **Server is down but network is up**: OfflinePage does NOT appear — detector only knows about transport-layer connectivity. You'll see individual API errors instead. **Known limitation.**
- **iOS Safari**: `navigator.onLine` is sometimes false-positive — browser quirk, no app-side fix.

### 6.3 Service worker — verify nothing critical is cached

1. DevTools → **Application → Service Workers** → status "activated and is running".
2. DevTools → **Application → Cache Storage** → expand the `workbox-precache-...` entry. Should contain: `index.html`, the main JS bundle (~2.5 MB), CSS, `/vite.svg`, the three icons. **Nothing else.**
3. Network tab → reload page → shell assets show Size `(ServiceWorker)` — they're cached.
4. **Navigate a library, click an item, play a video.** Network tab: all `/api/*`, `/cache/*`, `/hubs/*` responses show **network bytes**, NOT `(ServiceWorker)`. This is the critical contract — media and auth must always reach the network fresh.
5. Cache Storage → re-check after media playback: no entries for `/api/`, `/cache/`, or `/hubs/`. **If you find any, the runtime-caching contract was broken.**
6. **Deep-link offline**: DevTools Network → Offline → URL bar → type `/settings/client/general` → Enter. Shell loads from cache (no browser "no internet" page), React boots, OfflinePage takes over because `navigator.onLine` is false.

**Known limitations:**
- App shell is one 2.5 MB JS bundle, shell-precached. **After deploy, a hard refresh (Ctrl+Shift+R) is the most reliable way to force the new bundle** — autoUpdate activates the new SW on the next load, but the tab you're currently on is still running the old bundle.
- PWA is production-build-only. Dev server won't install or serve SW.
- No runtime caching by design. Lazy-loaded chunks added later won't work offline unless they match `globPatterns` at build time.
- **If you add a new server URL prefix later** (e.g. `/webhooks/`), add it to `navigateFallbackDenylist` in [`vite.config.ts:43`](src/SoftMedia.Client/vite.config.ts#L43) or the SW will serve the shell HTML for it.

## 7. Fix Match (admin metadata correction)

*P3-WI-003. Component: [`FixMatchCard.tsx`](src/SoftMedia.Client/src/components/admin/FixMatchCard.tsx). Renders at the top of every media detail page for admins only.*

**Prerequisites:** admin user, at least one media item (best: one whose auto-match is wrong, like a "Blade Runner 2049" file that matched the 1982 original), live network so providers can be queried.

**As a regular user first:** open any media detail page → confirm the FixMatchCard is **completely absent**. Then log out and back in as admin.

### 7.1 Re-search → Apply (the headline flow)

1. As admin, open the wrong-match item's detail page. A dark card sits above the type-specific view: wand icon + title "Fix match", two buttons "Re-search" (wand) and "Edit fields" (pencil).
2. Click **Re-search** → header collapses to a single X. Body shows: text input (pre-filled with current title) + narrow Year input + blue Search button.
3. Refine query (e.g. "Blade Runner 2049") + year (2017), click Search → spinner → scrollable candidate list. Each row: small poster, title with year in parens, optional grey subtitle (network, author, etc.), provider name, blue Apply button.
4. Click Apply on the right candidate → spinner on that row → green toast "Match applied — item locked".
5. **Card collapses back to idle** but now shows: **amber lock icon** + "Metadata locked" + small grey "since *<today>*". A third **amber Unlock button** has appeared.
6. The detail page above re-renders within ~1 s with the new title, poster, overview, year, etc.

### 7.2 Manual edit (typo fix / replace poster)

1. From idle, click **Edit fields** → form: Title text, Overview textarea, Year + Poster URL side by side, blue "Save (locks item)" button.
2. Fields pre-populate with current item values.
3. Change just the title, click Save → green "Saved — item locked" toast → card returns to locked-idle state.

### 7.3 Unlock

1. On a locked item, click amber **Unlock** → spinner → green "Unlocked" toast → card returns to "Fix match" wand-icon state. Unlock button vanishes.
2. **The next auto-refresh cycle will now re-pull provider metadata** and may overwrite your manual edits. That's the documented purpose of unlocking.

### 7.4 Edge cases

- **No matches**: query nonsense → grey hint "No matches. Try a shorter query or include the year." No toast (empty ≠ error).
- **Search provider error**: disconnect network briefly → red toast "Search failed".
- **Apply fails**: pick an odd Wikidata candidate with no usable record → red "Failed to apply match". Candidate list stays so you can try another row.
- **Wikidata non-film hits**: in a Movie library, search "Mercury" → you'll see the planet, the element, AND films. Use the grey subtitle/description column under each title to disambiguate. **This is by design** — Wikidata's `wbsearchentities` is type-agnostic and the alternative was unacceptable extra calls.
- **Two providers per Movie library**: you'll see one row per provider (Wikidata + OMDb) for the same film with different `providerName` labels. Both apply correctly; pick whichever has the better poster.
- **Year filter narrows results**: search "Blade Runner" with no year → both 1982 + 2017. With Year 2017 → 2017 ranks first / older entries drop.
- **Save with all blank fields**: still locks the item. The controller treats blanks as "preserve" (sends `undefined`). If you only want to lock without changes, this is the supported way — there's no separate "lock" button.
- **Poster URL accepts garbage**: type='url' will complain in the browser but the value is sent as-is. No server-side URL validation. You'll see a broken poster until you fix it.
- **Close mid-flow**: X closes, but Re-search and Edit modes preserve their form state until you switch items or reload. Re-opening Re-search reseeds the query from the current item title — your previous query text is lost.

### 7.5 Right vs. wrong

- **Right:** card hidden for non-admins. Header flips wand↔amber-lock correctly. Detail page above re-renders within ~1 s after Apply or Save (react-query invalidate). Toast wording matches the action.
- **Wrong:** card visible to non-admins (permission bug). Title/poster doesn't update after Apply (invalidation regressed). Lock icon doesn't appear after success (DB field not written). **Save with a blank Title field wipes the title** (`editTitle.trim() || undefined` regressed — blank should preserve, not overwrite). Helper line "Auto-refresh skips this item…" showing while in search/edit mode (should only render in idle).

### 7.6 Known limitations

- Wikidata search includes non-films. Use the description column. (See 7.4.)
- Movies fan out to 2 providers; expect duplicate-looking candidates with different `providerName`.
- Search "No matches" can be misleading when one of two providers errored silently — server logs the failure but UI only sees the survivor's empty result.
- After Unlock, the next auto-refresh cycle re-pulls provider metadata and may overwrite manual edits. That's the documented purpose.
- Candidate posters use `referrerPolicy="no-referrer"` and silently hide on error — broken/missing posters just show as blank squares. Intentional.
- Header buttons are ~28 px tall — fine on desktop, cramped on phone. Acceptable for admin-only tool.
